# 问题定位实战：下单接口跨用户删除购物车条目

> 一次真实的线上级缺陷排查记录。
> 核心方法：**问题单 + 接口响应 + 数据库记录** 三要素取证，逐步缩小范围。
> 全程使用 MySQL / Apifox / IDEA / Redis，可完整复跑。

---

## 一、问题单

| 项 | 内容 |
|---|---|
| 现象 | 用户在浏览商品、加购过程中，购物车里的条目会莫名减少，且**没有产生任何订单** |
| 复现率 | 单人操作复现不出来，只在**多用户同时使用**的环境里偶发 |
| 初始判断 | 曾被怀疑是"购物车被按用户整体清空"或"定时任务误删"——都被证据否掉了 |

对应的接口测试用例：

| 用例号 | 目的 | 步骤 | 预期 |
|---|---|---|---|
| TC-ORDER-012 | 核验下单接口对 `cartItemIds` 的**归属校验**是否完整 | 用 **A 用户**的 token 调 `POST /user/order/submit`，`cartItemIds` 里混入**不属于自己**的购物车 id | 非本人条目应被忽略或拒绝，**任何其他用户的数据都不应被修改** |

## 二、现场构造（可复跑）

```
shopping_cart 初始状态：
  id=4  user_id=1  拍黄瓜    8.00    ← A 用户（zhangsan）本人
  id=5  user_id=2  机械键盘  32.00   ← B 用户（lisi）
  id=6  user_id=2  红烧牛肉  48.00   ← B 用户（lisi）
  id=7  user_id=2  无线鼠标  18.00   ← B 用户（lisi）

orders 基线：MAX(id) = 131073
operation_log 基线：MAX(id) = 48
```

发起请求（用 A 用户的 token）：

```
POST /user/order/submit
header  token: <A 用户的 JWT>
```
```json
{
  "consignee": "费呀",
  "phone": "13800000000",
  "address": "上海市浦东新区科苑路 100 号",
  "remark": "越权用例",
  "payMethod": 1,
  "cartItemIds": [4, 5, 6]
}
```
> 5、6 是 B 用户的条目。

## 三、三要素取证

### ① 接口响应 —— 完全正常，什么都没说

```
HTTP 200 | code: 1 | 3.8ms
{ "id": 131074, "orderNumber": "1790139073114008177", "orderAmount": 8.00, "status": 1 }
```

请求里带了 3 个 id，返回却是妥妥的成功，还分配了订单号。
**只看接口层，会直接判定"功能正常"。**

但这里已经埋了一条线索：

| 商品 | 单价 | 归属 |
|---|---|---|
| 拍黄瓜 | 8.00 | A 用户（本人） |
| 机械键盘 | 32.00 | B 用户 |
| 红烧牛肉 | 48.00 | B 用户 |

若服务端把 3 条都当成 A 用户的，金额应是 **88.00**。它算出 **8.00** ——
**说明查询/计算侧确实按 `userId` 过滤过，服务端明确知道 5、6 不是 A 的。**

### ② 数据库记录 —— 决定性证据

```sql
SELECT id, user_id, name, amount FROM shopping_cart ORDER BY id;
```
```
id | user_id | name
7  | 2       | 无线鼠标      ← 只剩 1 行（基线 4 行）
```

```sql
SELECT id, user_id, amount FROM orders WHERE id > 131073;
SELECT order_id, name, amount FROM order_detail WHERE order_id > 131073;
```
```
131074 | 1 | 8.00                                   ← 只有 A 用户的订单
131074 | 拍黄瓜 | 8.00                            ← 只有 1 条明细
```

**B 用户的购物车被删了 2 条，而 B 用户什么订单都没得到。**

### ③ 操作日志 —— 查不到

```sql
SELECT id, oper_user, oper_module, oper_type, oper_time
FROM operation_log ORDER BY id DESC LIMIT 10;
```
最新一条仍是 `id=48`（12:17 的 admin 登录），**这次下单没有产生任何记录**。
→ 这本身是一条线索：说明**用户端写操作没有留痕**（见第六节）。

## 四、四步缩小范围

### 三个集合一对照，结论就出来了

| 集合 | 内容 |
|---|---|
| 请求入参 `cartItemIds` | **4, 5, 6** |
| 服务端认定的本人条目（订单金额/明细来源） | **4** |
| 实际被删除的 | **4, 5, 6** ← 和入参**一模一样** |
| 幸存 | **7**（唯一没写进入参的） |

### 推理链

1. **不是"按用户清空"** —— B 用户的购物车还剩 1 条（id=7）。若是清空，应一条不剩 → 是**定点删除**。
2. **删的是零散 id** —— 删 5、6 留 7。只有"按 id 列表删"才会出现这种结果。
3. **被删集合 == 请求入参集合** —— 4、5、6 全没了，7 留着。
   **删除范围直接来自请求参数，与"是否本人"无关。**
4. **但金额和明细只认了本人条目**（8.00）。
   同一个方法里，**查询侧用 `userId` 过滤了，删除侧没有** ——
   **校验用的数据和产生副作用的数据不是同一个。**

## 五、根因

`src/main/java/com/mall/service/OrderService.java`

| 行 | 代码 | 结论 |
|---|---|---|
| 72-75 | `selectList(... .in(ShoppingCart::getId, dto.getCartItemIds()).eq(ShoppingCart::getUserId, userId))` | 查询侧**有**归属校验 ✅ |
| 112 | `shoppingCartMapper.deleteBatchIds(dto.getCartItemIds())` | 删除侧**直接采信入参 id**，无任何条件 ❌ |

### 为什么说"不是漏写条件，而是选错了 API"

`deleteBatchIds` 是 MyBatis-Plus 的**按主键批量删**方法 ——
它在**结构上就不接受 where 条件**。所以不是"忘了加 `.eq(userId, ...)`"，
而是这个 API 根本没有地方给你加。

> **一句话总结**：查询阶段做的归属校验，没有传递到删除阶段；
> 副作用直接采信了不可信的原始入参。

## 六、修复与回归

### 修复（`OrderService.java:111-114`）

```java
// 清除已下单的购物车条目
shoppingCartMapper.delete(new LambdaQueryWrapper<ShoppingCart>()
        .in(ShoppingCart::getId, dto.getCartItemIds())
        .eq(ShoppingCart::getUserId, userId));
```

> 备选方案（更彻底）：让删除范围直接取自**已经校验过的** `cartItems` 集合 ——
> `deleteBatchIds(cartItems.stream().map(ShoppingCart::getId).toList())`。
> 这样"删除范围"和"订单明细来源"来自**同一个数据源**，结构上不可能再不一致。
> 本方案保留了"条件显式写在删除语句上"的可读性，代价是同一个约束在两处各写了一遍。

### 回归（重新铺现场，id 全变）

```
shopping_cart: id=8(uid1) 9(uid2) 10(uid2) 11(uid2)
请求: cartItemIds = [8, 9, 10]      ← 同样的越权构造
```

| 验收项 | 修复前 | 修复后（Apifox 观察） | 修复后（独立查库） |
|---|---|---|---|
| B 用户剩余 | 1 条 ❌ | **3 条**（9/10/11） | **3 条**（9/10/11）✅ |
| 本人条目 id=8 | 被删 | 已删除 | 已删除 ✅ |
| `orders` | 131074 / uid=1 / 8.00 | 131075 / uid=1 / 8.00 | 131075 / uid=1 / 8.00 ✅ |
| `order_detail` | 拍黄瓜 8.00 | 拍黄瓜 8.00 | 拍黄瓜 8.00 ✅ |

**同一个越权请求：改之前对方丢 2 条，改之后一条不少。**
回归采用**两侧独立观察互校**（Apifox 侧 + 直接查库侧），逐行一致才算通过。

## 七、顺带补齐的三处观测缺口

排查过程本身暴露了三个让"事故无法追溯"的基础设施问题，一并修掉：

| # | 问题 | 证据 | 修复 |
|---|---|---|---|
| 1 | **没有文件日志**，日志只进控制台，滚屏即丢失 | 项目根目录无 `logs/` | `logging.file.name: logs/mall-order.log` + 10MB 滚动 / 保留 7 天 |
| 2 | **SQL 不落盘** —— `StdOutImpl` 走 `System.out`，绕开 logback | 日志文件里一条 SQL 都没有 | 改 `Slf4jImpl`，**并补 `logging.level.com.mall.mapper: debug`**（否则 SQL 走 DEBUG 被 info 挡掉） |
| 3 | **用户端写操作零留痕** —— `@AutoLog` 只挂在管理端 5 个 Controller 上 | `operation_log` 里查不到任何下单记录 | 给 `submit` / `paySuccess` / `cancel` 补注解 |

修完之后日志形如：

```
DEBUG c.t.m.ShoppingCartMapper.selectList : ==>  Preparing: SELECT ... FROM shopping_cart WHERE (user_id = ? AND dish_id = ? AND dish_flavor = ?)
DEBUG c.t.m.ShoppingCartMapper.selectList : ==> Parameters: 1(Long), 1(Long), (String)
DEBUG c.t.m.ShoppingCartMapper.selectList : <==      Total: 0
DEBUG c.t.m.ShoppingCartMapper.insert     : ==> Parameters: 1(Long), 1(Long), 拍黄瓜(String), 8.00(BigDecimal), 1(Integer)
DEBUG c.t.m.ShoppingCartMapper.insert     : <==    Updates: 1
```

**三行一组（Preparing / Parameters / Total）就是一条 SQL 的完整履历** ——
一次"加购"的调用链（查重 → 取商品价 → 落库）被日志完整摊开，
不用再跳三个文件去拼。

## 八、遗留问题

排查路上发现但未在本次处理的问题，已登记：

1. **`operation_log` 不区分成功/失败。**
   切面在 `finally` 里**无条件**写日志，且实体没有 `status` / `error_msg` 字段。
   实测：正常下单 `id=49`，异常用例（购物车为空）`id=50`、`id=51` —— **三行完全同型**。
   → 后果：翻日志只能知道"有人尝试下单"，不知道成没成。
   → 修法：加字段，或拆成 `@AfterReturning` + `@AfterThrowing`。

2. **业务异常返回 HTTP 200。**
   `{"code":0,"msg":"购物车为空，不能下单"}` 的状态码是 **200**。
   网关、监控、告警全按 2xx 统计，**线上失败率永远是 0**。
   → 修法：业务异常按语义返回 4xx（参数类 400 / 冲突 409 / 权限 403）。

3. **幂等锁释放时机早于事务提交。**
   `submit()` 里 Redis 锁在 `finally` 释放，而 `finally` 执行在
   `@Transactional` **提交之前** → 并发下第二个请求可能读到未提交的购物车，幂等保证被削弱。

4. **`oper_params` 与 `Parameters` 含 PII。**
   收货人、电话、地址被原样写进日志与数据库。上线前需脱敏或关闭参数记录。

## 十、可迁移的方法论

1. **接口返回成功 ≠ 业务正确。**
   本例接口全程 `200 + code:1`，破坏发生在数据库里。
   **只看接口响应会百分之百漏掉这类缺陷** —— 涉及"副作用"的验证，必须查库。

2. **用 AOP 切面的"必写"特性做请求到达判定器。**
   切面在 `finally` 中无条件写日志 ⇒
   **有记录 = 请求进过 Controller；无记录 = 卡在更前面（反序列化 / 鉴权 / 网络）。**
   这把日志从"噪音"变成了"证据"，可以直接用来划分故障域边界。

3. **不要只看"改动是否生效"，要找"改动之间的不一致"。**
   本例的破案点是两个集合的差异：
   **查询用的集合（过滤后）** vs **删除用的集合（未过滤）**。
   "校验"和"副作用"用了不同的数据源 —— 这是一整类缺陷的通用特征。

4. **回归必须两侧独立观察互校。**
   Apifox 侧看到的和直接查库看到的，逐行一致才算通过。
   只信自己那一侧的观察，会把"查询缓存/脏读/序列化问题"当成通过。
