## 四、关键验收点（挑有信息量的）

### 4.1 新增员工：断言打到副作用，不只打返回值

接口返回 `code=1` **不等于**数据对。四条判据缺一不可：

| 判据 | 断言 | 结果 |
|---|---|---|
| 行真的落库 | 直接查库能查到该行 | PASS |
| 密码是摘要而非明文 | 库中 password 为 SHA-256 摘要 | PASS |
| 默认值由应用显式设置 | `status=1` 来自代码而非 DB 兜底 | PASS |
| 摘要口径正确 | **用明文密码反向登录能成功** | PASS |

> 最后一条是重点：前三条只能证明"写进去了"，只有反向登录才能证明"写对的口径"。

### 4.2 编辑员工：DTO 白名单是安全边界

`EmployeeUpdateDTO` 只暴露 `name` / `phone` 两个字段。验收不只是"能改对"，更要证明**不能改错的**：

| 断言 | 结果 |
|---|---|
| 请求体夹带 `password` → 密码未被改动 | PASS |
| 请求体夹带 `username` → 用户名未被改动 | PASS |
| 请求体夹带 `status` → 状态未被改动 | PASS |
| 夹带进来的密码**不能**用于登录（二次确认） | PASS |
| 只传 name、不传 phone → phone 保持不变（未被 null 清空） | PASS |
| 文档层面反向断言：`EmployeeUpdateDTO` 的 schema 不含上述 4 字段 | PASS |

> 依据：MyBatis-Plus `updateById` 默认字段策略为 `NOT_NULL` —— **null 字段不进 SQL**。
> 这既是保护（不误清数据），也是陷阱（想"清空某字段"时会静默不生效）。

### 4.3 分页查询：三层证据链

`pageSize=-1` 曾经**看起来是正常的**——因为框架 `maxLimit` 仍会给 SQL 加上 `LIMIT`。
只断言返回值发现不了，因此本脚本的判据分三层：

1. **返回值**：`pageSize=-1` 被归一化为默认 10 条
2. **查库交叉核验**：`total` 等于 DB 真实行数、末页条数正确、按 id 倒序
3. **SQL 日志证据**：本次请求新增的日志里**必须同时出现 `LIMIT` 和 `COUNT(*)`**

> 第 3 层的价值：`maxLimit` 的参数判定条件是 `(size > limit || size < 0)`，
> 它夹得住 `LIMIT`，但 `COUNT` 查询在拦截器之前就已执行 ——
> **`LIMIT` 存在 ≠ 分页正确**。只断言 SQL 里有 LIMIT 会漏掉这个缺陷。

### 4.4 启用禁用：非法值必须被拦在入库之前

`status` 在库里是 `tinyint`，能存 `-128~127`。所以判据必须包含「**库里没被写成非法值**」，
只断言「接口返回 code=0」是不够的。

| 输入 | 期望 | 结果 |
|---|---|---|
| `status=2` / `5` / `-1` / `99` | 拒绝 + 提示状态不合法 + 库里 status 仍只有 0/1 | PASS |
| 禁用自己 | 拒绝，提示「不能禁用自己」，且自己仍能登录（未 lockout） | PASS |
| 重复禁用同一人 | 幂等，仍返回成功 | PASS |
| 被禁用的账号登录 | 拒绝，提示「账号已被禁用」 | PASS |
| 不存在的 id | 不假成功，提示「员工不存在」 | PASS |
| `id` 少一段路径参数 | 404，不误作用到其他行 | PASS |

## 五、缺陷与处置

### 5.1 本轮发现并关闭：BUG-20260923-001（分页入参未归一化）

一次提交声称修好，实测**只修了 1/3**。同一个缺陷单里其实藏了 **2 处独立缺陷**：

| # | 缺陷 | 为什么第一次没发现 |
|---|---|---|
| 1 | 归一化后的 `pageNum`/`pageSize` 算出来了却没用于 `new Page<>()` | 返回值看着对（框架 `maxLimit` 兜了底），COUNT 却被跳过 |
| 2 | 白名单条件写成 `ENABLE.equals(s) && DISABLE.equals(s)` —— **恒为假**，校验形同虚设 | 非法值恰好命中"不过滤"分支，`total=0` 看起来像个正常空结果 |

**处置**：两处均已修复，复验 32 通过 / 0 失败。修复要点：Service 层在 `new Page<>()` 之前就完成归一化，
不能依赖 `maxLimit` 兜底。

### 5.2 登记待修（XFAIL，归 M4）

| 用例 | 现象 | 根因 | 归属 |
|---|---|---|---|
| C7.1 | `page=abc` 返回 200 + "系统繁忙" | 全局异常处理器把参数类型异常吞成 200 | M4 |
| C7.2 | `pageSize=abc` 同上 | 同上 | M4 |

> **为什么登记为 XFAIL 而不是让它红着**：这两条的根因在别的模块。
> 若与真故障混在一个桶里，CI 会永远红着，真回归失败就被已知噪音淹没 ——
> 那正是缺陷① 本身的后果。实现上 XFAIL 会打印、会计数，但**不影响退出码**；
> 哪天变绿会打印 `[XPASS]` 提醒转成正向断言。

### 5.3 观测到的遗留问题（不影响本次验收）

| 项 | 现象 | 影响 |
|---|---|---|
| 禁用未即时吊销令牌 | 禁用员工后，其**已签发的旧 token 仍可继续访问**，直到自然过期 | 安全项，需引入令牌黑名单/版本号，归后续迭代 |

## 七、验收方法的局限（诚实声明）

1. **接口响应时间是单线程串行**，未做并发压测。本记录不包含 QPS/吞吐指标；
   并发场景仅覆盖「新增员工同时提交」这一类正确性用例（用 `Barrier` 卡齐后同时发）。
2. **`m2_page_verify.py` 的分页断言依赖库的起始行数**（如 `total == DB 真实行数(26)`、
   `末页恰好 6 条`）。因此该脚本**必须幂等**：跑前不清库就会读到上一轮的残渣而假红。
   实测中确实踩过一次（第二次跑 M2-1 假红 31/1，实为残留数据污染，非代码退化）。
   现已由聚合脚本统一做**双向清扫**保证幂等。
3. **XFAIL 的 2 条本轮不会转绿**，属正常预期，不代表"还有 2 个问题没解决"。
4. 脚本以 `urllib` + 直连 MySQL 做双向核验；Apifox 用于演示与手工验证，
   **两者分工不同，不互相替代**。
