# 缺陷修复清单（8 处）

> 本文档汇总已修复的数据一致性与并发缺陷，每条写清：**现象 → 根因 → 修复方式 → 证据（可复跑的验收）**。

| # | 缺陷 | 类型 | 根因 | 修复方式 | 证据 |
|---|---|---|---|---|---|
| 1 | 购物车加购并发丢更新 | 并发 | 「先查后写」绝对值写：并发请求读到同一个旧 number、各自 +1，后写的覆盖先写的，接口全返回成功但数量少涨 | 改相对量原子写 `number = number + 1`；减购拆成 `number > 1` 自减 + `number = 1` 删除两条语句 | 提交 `6469e3a`；`m3_cart_race.py` 案例 A/B（串行 20 次、并发 20 次均 1 行 20 件） |
| 2 | 喜好为 NULL 时唯一约束整条失效 | 数据一致性 | 唯一键建在可空列上，而 SQL 三值逻辑里 `NULL = NULL` 恒为假，组合套装行（dish_id 为 NULL）之间永远判不出重复 | 喜好归一为 `''` 并把列收紧为 `NOT NULL DEFAULT ''`；新增生成列 `dish_key/setmeal_key = IFNULL(...,0)`，唯一键建在生成列上 | 提交 `6469e3a`；`m3_cart_race.py` 案例 C/E（唯一约束守门、组合套装侧 NULL） |
| 3 | 并发插入同一购物车条目产生重复行 | 数据一致性 | 自增与插入之间存在窗口，两个线程可能都走"新建"分支 | 唯一键兜底，插入被拒时回退为一次自增并留日志（不把异常静默吞成"已存在"） | 提交 `6469e3a`；`m3_cart_race.py` 案例 B/T2 |
| 4 | 订单状态流转被并发绕过（业务规则失效） | 并发 | 状态流转是「查出来 → Java 判状态机 → updateById 写绝对值」，发货与取消并发时两边都读到待发货、各自算出合法目标状态，后写的覆盖先写的，**两条路径都返回成功** | `OrdersMapper#casStatus`：`UPDATE ... WHERE id=? AND status=?`，判断与写入同一条语句由行锁串行化；影响 0 行即判负并返回"订单状态已变更" | 提交 `09490ce`；`m3_order_state_race.py` 案例 C/D，修复前 **40/40 轮命中**，修复后 **0/40** |
| 5 | 下单可删除他人购物车条目（越权） | 数据一致性/安全 | 下单只按 `cartItemIds` 删条目，未校验这些条目属于当前用户，A 用户可把 B 用户的条目删掉，且不产生订单 | 查询与删除都加 `user_id = 当前用户` 条件，非本人条目一律不采信 | 提交 `708372c`；`docs/问题定位实战-跨用户越权删除.md`（完整取证记录，可复跑） |
| 6 | 员工分页 total 与列表口径不一致 | 数据一致性 | 依赖 MyBatis-Plus 的 `maxLimit` 兜底，但它只夹得住 `LIMIT`，`COUNT` 在拦截器之前就已执行，翻页时出现总数与实际条数对不上 | 分页入参在 Service 层归一化（页码下限 1、页大小 10~100）后再进分页插件，不依赖 `maxLimit` 兜底 | 提交 `70bd56a`；`m2_page_verify.py` 32 条断言 |
| 7 | 编辑员工可夹带改密码/改状态/改用户名 | 数据一致性 | 更新 DTO 字段过宽，`EmployeeUpdateDTO` 直接承接前端对象，夹带的 `password/username/status` 会被一起写入 | DTO 收敛为 `name/phone` 白名单，请求体里夹带的其它字段一律不生效 | 提交 `70bd56a`；`m2_update_verify.py` 34 条断言 |
| 8 | 库存超卖与超时取消后的库存重复回补 | 数据一致性/并发 | 无库存扣减；且"取消"这个动作没有唯一的赢家判定，多副本/消息重投会各自回补一次 | 下单走 `stock = stock - n AND stock >= n`（影响 0 行即库存不足，事务回滚）；超时取消的取消权由 `casStatus` 判定，**只有赢家回补** | 提交 `09490ce`；`OrderTimeoutServiceTest` 5 条（含 8 线程并发只有 1 个赢家、库存只回补 1 次） |
