## 二、Explain 执行计划对比

管理端订单分页查询：`WHERE status=? AND order_time BETWEEN ? AND ? ORDER BY order_time DESC LIMIT 20`

| | 优化前（无联合索引） | 优化后（idx_status_order_time） |
|---|---|---|
| type | **ALL**（全表扫描） | **range**（索引范围扫描） |
| key | NULL | idx_status_order_time |
| rows | 99,398 | 1,356 |
| Extra | Using where; **Using filesort** | Using index condition; **Backward index scan** |

**关键点**：扫描行数 99,398 → 1,356（减少 98.6%），且 `Using filesort` 消失——排序改由索引有序性提供。

## 三、SQL 层实测（performance_schema，每场景 50 次）

耗时取自 `events_statements_summary_by_digest`，只统计 SQL 本身，不含客户端开销。

| 场景 | 优化前 | 优化后 | 平均扫描行数（前 → 后） | 耗时下降 |
|------|--------|--------|--------------------------|----------|
| 订单明细 `WHERE order_id=?` | **694.07 ms** | 0.79 ms | 250,002 → 2 | 99.9% |
| 订单浅分页 `status+时间范围` | **529.73 ms** | 0.23 ms | 100,022 → 20 | 99.96% |
| 订单深分页 `LIMIT 5000,20` | **575.71 ms** | 58.33 ms | 105,022 → 5,020 | 89.9% |
| 用户历史订单 `WHERE user_id=?` | **504.83 ms** | 0.33 ms | 100,022 → 20 | 99.9% |

## 四、接口层实测（HTTP，预热后稳态，每接口 40 次）

这才是「接口响应时间」的口径（含 HTTP + 序列化 + 应用层开销）。
**测量方法**：先打 30 次预热（消除 JIT 与连接预热干扰），再采样 40 次统计 avg / P95。

| 接口 | 优化前 | 优化后 | 耗时下降 |
|------|--------|--------|----------|
| 用户历史订单 `GET /user/order/history` | 321.7 ms（P95 373） | **12.8 ms**（P95 29） | **96.0%** |
| 订单详情 `GET /user/order/{id}` | 364.2 ms（P95 401） | **12.1 ms**（P95 27） | **96.7%** |
| 管理端订单分页 `GET /admin/order/page` | 339.0 ms（P95 390） | **22.8 ms**（P95 46） | **93.3%** |
| C端商品列表 `GET /user/dish/list`（走缓存） | 17.0 ms | 20.5 ms | 不受索引影响（对照组 ✓） |

> 对照组说明：商品列表接口全程命中缓存，索引增删前后耗时基本不变，证明上述差异确实来自索引优化，而非测量噪声。

## 五、缓存实测（Cache Aside）

| 场景 | 平均耗时 | 命中率 |
|------|----------|--------|
| 纯读 200 次 | 21.7 ms（P95 47） | 100%（hit 200 / miss 0） |
| **读写混合 220 次（每 11 次 1 次写，写占比 9%）** | — | **90.5%**（hit 181 / miss 19） |
| **无缓存（每次读前删 key，强制回源 DB）** | **877.6 ms**（P95 2275） | 0%（全部 miss） |

**缓存收益**：877.6 ms → 21.7 ms，**数据库查询耗时下降 97.5%**。

> 命中率口径说明：纯读场景下命中率趋近 100%；真实业务必然存在写操作（改价、上下架）触发缓存失效，
> 因此采用「9% 写 + 91% 读」的混合场景作为命中率口径，实测 90.5%。

## 六、结论汇总

| 优化项 | 优化前 | 优化后 | 降幅 |
|--------|--------|--------|------|
| 订单详情接口（HTTP） | 364.2 ms | **12.1 ms** | **96.7%** |
| 订单分页接口（HTTP） | 339.0 ms | **22.8 ms** | **93.3%** |
| 用户历史订单（HTTP） | 321.7 ms | **12.8 ms** | **96.0%** |
| 订单明细 SQL | 694.07 ms | **0.79 ms** | **99.9%** |
| 缓存收益（单次读） | 877.6 ms | **21.7 ms** | **97.5%** |
| 缓存命中率（9% 写 + 91% 读混合） | — | **90.5%** | — |

**结论**：

1. 联合索引把高频查询从全表扫描（`type=ALL` + `Using filesort`）转为索引范围扫描
   （`type=range` + `Backward index scan`），扫描行数 99,398 → 1,356，接口响应降至十分之一以内；
2. Cache Aside 在读写混合场景下命中率约 90%，命中场景读耗时相比回源数据库下降约 97%；
3. 对照组（全程命中缓存的商品列表）在索引增删前后耗时基本不变，说明上述差异来自索引与缓存改造本身。

> ```

## 八、诚实声明（测量方法的局限）

1. **必须预热后再测**：未预热时首次测量受 JIT 编译、连接池初始化、InnoDB buffer pool 冷启动影响。
   实测中曾出现「无索引反而更快」的假象，根因就是两次测量的系统热度不同，后改为「预热 30 次再采样」。
2. **buffer pool 冷热影响绝对值**：刚造完数据立即测，全表扫描可达 700 ms+；数据完全驻留内存后约 500 ms。
   报告中的数字为预热后的**稳态值**。
3. **压测工具是 curl 而非 JMeter**：并发能力有限，本报告指标为**单线程串行请求的响应时间**，
   非高并发 QPS 压测。若需并发场景数据，用 `docs/jmeter/mall-perf.jmx` 在 JMeter 中跑。
